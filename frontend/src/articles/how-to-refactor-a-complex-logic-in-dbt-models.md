<h3>Guiding Principles</h3><h4>Core Philosophy: “Build Up, Don’t Pile On”</h4><ul><li><strong>Separation of Concerns</strong>: Each model should have a distinct and clear purpose.</li><li><strong>Progressive Enrichment</strong>: Introduce complexity incrementally, adding layers as needed.</li><li><strong>Domain-Driven Design</strong>: Organise related logic into cohesive groups.</li><li><strong>Reusability First</strong>: Prioritise designs that accommodate multiple use cases.</li><li><strong>Test at Every Layer</strong>: Validate functionality continuously, rather than waiting until the end.</li></ul><h3>When to Break Down Models</h3><h3>How to Break Down Complex Models</h3><p>A common challenge in data engineering is managing complex SQL models with numerous joins and transformations. A single, monolithic model can become a maintenance nightmare, making debugging and updates difficult. The solution is to break down the model into a series of <strong>intermediate models</strong>.</p><p>This layered approach offers several benefits:</p><ul><li><strong>Clear Data Lineage:</strong> Each model builds logically on the previous one.</li><li><strong>Simplified Debugging:</strong> If an issue arises, you can isolate it to a specific layer.</li><li><strong>Incremental Development:</strong> You can build and test each layer independently.</li><li><strong>Reusability:</strong> A foundational model can be reused by multiple downstream models.</li></ul><p>Below is a generic refactoring of a complex SQL model, demonstrating how to break it down into a logical sequence of intermediate models.</p><h3>1. The Foundation Layer: <code>intermediate_core.sql</code></h3><p>This first model establishes the base of your data model. It should include the most critical tables and columns, forming a central “core” dataset that subsequent models will build upon. The goal is to perform only the essential joins and select the foundational data points.</p><pre spellcheck="false">-- This model forms the foundational dataset by selecting core fields<br />-- from primary staging tables.<br />{{ config(materialized = &#x27;table&#x27;) }}<br /><br />with<br />-- Select from the main subject table<br />base_subject as (<br /> select * from {{ ref(&#x27;stg_main_subject_table&#x27;) }}<br />),<br />-- Join with a key related table<br />related_table_a as (<br /> select * from {{ ref(&#x27;stg_related_table_a&#x27;) }}<br />),<br />-- Join with another essential table<br />related_table_b as (<br /> select * from {{ ref(&#x27;stg_related_table_b&#x27;) }}<br />)<br />select<br /> -- Core fields from the main table<br /> base_subject.primary_key,<br /> base_subject.core_field_1,<br /> base_subject.core_field_2,<br /> -- Joining key fields<br /> related_table_a.lookup_key_a,<br /> related_table_b.lookup_key_b,<br /> -- Create a surrogate key for the entity<br /> {{ dbt_utils.generate_surrogate_key([&#x27;base_subject.primary_key&#x27;]) }} as entity_surrogate_key<br />from base_subject<br />left join related_table_a<br /> on base_subject.common_id = related_table_a.common_id<br />inner join related_table_b<br /> on base_subject.another_id = related_table_b.another_id</pre><h3>2. The Enrichment Layer: <code>intermediate_enrichment.sql</code></h3><p>This model takes the core dataset from the previous layer and enriches it with additional information from other sources. This is where you would typically join in more granular data or supplementary attributes.</p><pre spellcheck="false">-- This model enriches the core dataset with additional attributes<br />-- from other staging tables.<br />{{ config(materialized = &#x27;table&#x27;) }}<br /><br />with<br />-- Reference the core model from the previous step<br />core_data as (<br /> select * from {{ ref(&#x27;intermediate_core&#x27;) }}<br />),<br />-- Select from a table with supplemental data<br />supplementary_data as (<br /> select * from {{ ref(&#x27;stg_supplementary_data&#x27;) }}<br />),<br />-- Select from a table with dimension data<br />dimension_data as (<br /> select * from {{ ref(&#x27;stg_dimension_data&#x27;) }}<br />)<br />select<br /> -- Select all columns from the previous model<br /> core_data.*,<br /> -- Add new, enriched fields<br /> supplementary_data.extra_attribute,<br /> supplementary_data.derived_field,<br /> dimension_data.dimension_value<br />from core_data<br />left join supplementary_data<br /> on core_data.primary_key = supplementary_data.primary_key<br />left join dimension_data<br /> on core_data.lookup_key_a = dimension_data.lookup_key_a</pre><h3>3. The Final Transformation Layer: <code>final_model.sql</code></h3><p>This final model brings everything together. It’s where you apply the last set of business logic, such as <code>CASE</code> statements, data type casting, and final column selection. This layer also handles data lineage and slowly changing dimension (SCD) logic to prepare the data for consumption.</p><pre spellcheck="false">-- This is the final model, where all transformations are complete.<br />-- It selects and casts the final set of columns for end-user consumption.<br />{{ config(materialized = &#x27;table&#x27;) }}<br /><br />with<br />-- Reference the enriched data from the previous layer<br />enriched_records as (<br /> select * from {{ ref(&#x27;intermediate_enrichment&#x27;) }}<br />),<br /><br />final_transformations as (<br /> select<br /> -- Casting key IDs to appropriate types<br /> primary_key::varchar(50) as final_entity_id,<br /> entity_surrogate_key,<br /> -- Applying business logic with a CASE statement<br /> case<br /> when primary_key like &#x27;ABC%&#x27; then &#x27;Type A&#x27;<br /> else &#x27;Type B&#x27;<br /> end as entity_type,<br /> -- Final column selection and aliasing<br /> core_field_1 as final_attribute_1,<br /> derived_field as final_attribute_2,<br /> extra_attribute as final_attribute_3,<br /> -- Example of SCD Type 2 logic<br /> effective_start_date as eff_start_dttm,<br /> case<br /> when is_deleted_flag then current_timestamp<br /> else &#x27;9999-12-31 23:59:59&#x27;::timestamp<br /> end as eff_end_dttm<br /> from enriched_records<br />)<br /><br />-- Final SELECT statement to materialize the model<br />select * from final_transformations</pre>
