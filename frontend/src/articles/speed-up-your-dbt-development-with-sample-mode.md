<p>We have all been there. You make a small change to your dbt model, run <code>dbt build</code>, and then wait. And wait. Sometimes for minutes, sometimes longer. Meanwhile, your cloud warehouse is churning through millions of rows just so you can verify a simple join logic or test a new transformation.</p><p>What if you could slash that development time dramatically?</p><h3>Introducing the — sample Flag</h3><p>The <code>--sample</code> flag is a powerful new addition to dbt that changes the game for development workflows. This feature lets you work with time-filtered subsets of your data during development, dramatically reducing build times and warehouse compute costs.</p><p>Instead of processing your entire dataset every time you test a change, sample mode lets you work with recent data that’s actually relevant to your development needs. Think of it as a fast-forward button for your development cycle.</p><h3>How Sample Mode Works</h3><p>Sample mode uses <strong>time-based filtering</strong> rather than row limiting. You specify a time period, and dbt automatically filters your source tables and models to include only data within that timeframe.</p><p>The flag is available for <code>dbt run</code> and <code>dbt build</code> commands:</p><pre spellcheck="false">dbt build --sample=&quot;3 days&quot;</pre><p>This samples data from the last 3 days across your entire project. Your source tables get filtered, and that reduced dataset flows through all your downstream models automatically.</p><h3>Configuring Event Time</h3><p>Because sample mode uses time-based filtering, you need to specify which timestamp column to use. This is done through the <code>event_time</code> configuration on your models and sources:</p><pre spellcheck="false">models:<br /> - name: stg_orders<br /> config:<br /> event_time: order_created_at</pre><p>This tells dbt which column to use when applying the time filters during sampling.</p><h3>Two Sampling Approaches</h3><p>Sample mode supports two ways to specify time ranges:</p><p><strong>Relative Time Specs</strong> — Filter data backwards from when you run the command:</p><pre spellcheck="false">dbt run --sample=&quot;6 hours&quot;<br />dbt run --sample=&quot;3 days&quot;<br />dbt run --sample=&quot;2 months&quot;</pre><p>Supported granularities: hours, days, months, years</p><p><strong>Static Time Specs</strong> — Define an exact time window:</p><pre spellcheck="false">dbt run --sample=&quot;{&#x27;start&#x27;: &#x27;2024-07-01&#x27;, &#x27;end&#x27;: &#x27;2024-07-08 18:00:00&#x27;}&quot;</pre><p>This approach is perfect when you want to test your models against a specific period, like your busiest week or a time when you know edge cases occurred.</p><h3>Real Impact on Development Speed</h3><p>Let’s talk about what this means in practice. Imagine you’re working on a large fact table with billions of rows that typically takes 8 minutes to build. With sample mode filtering to just 3 days of data, that same model might build in under a minute.</p><p>For a typical development session where you’re iterating on logic, testing edge cases, and refining transformations, you might run <code>dbt build</code> a dozen times. Without sampling, that&#39;s over an hour and a half of waiting. With sampling? Maybe 15 minutes.</p><p>That’s time you get back to actually think about your data models, not watch progress bars.</p><h3>Perfect for CI/CD Pipelines</h3><p>Sample mode isn’t just for local development. It’s a powerful tool for your continuous integration pipelines. When a developer opens a pull request, your CI system can run a quick sanity check using sampled data before committing to a full build.</p><p>This creates a faster feedback loop. Developers know within minutes if their changes break anything, rather than waiting for a full data refresh. You catch syntax errors, logical mistakes, and broken references early — when they’re cheapest to fix.</p><img src="https://cdn-images-1.medium.com/max/800/1*oCUbwMsEvx_bOibEsAB4Jw.png" alt="" /><h3>Working with Recent Data</h3><p>Here’s where sample mode really shines: when you use relative time specifications like “3 days”, you’re automatically working with your most recent data patterns. This often makes your testing more relevant than running against years of historical data.</p><p>Recent data reflects:</p><ul><li>Current business patterns and seasonality</li><li>Latest schema changes</li><li>Recent edge cases and data quality issues</li><li>Active customer behavior</li></ul><p>This isn’t just faster — it’s often more meaningful for development and testing purposes.</p><h3>Controlling What Gets Sampled</h3><p>Sometimes you don’t want certain refs to be sampled. Maybe it’s a small dimension table, or a critical reference that needs full data. You can prevent sampling by appending <code>.render()</code>:</p><pre spellcheck="false">with source as (<br /> select * from {{ ref(&#x27;stg_customers&#x27;).render() }}<br />),<br />...</pre><p>This gives you surgical control over which parts of your DAG use sampled data.</p><h3>When to Use Sample Mode</h3><p>Sample mode excels in specific scenarios:</p><p><strong>During active development</strong>: When you’re iterating on model logic and need quick feedback loops.</p><p><strong>In CI/CD checks</strong>: For fast validation before running full production builds.</p><p><strong>For schema testing</strong>: When you need to verify column names, data types, and basic transformations.</p><p><strong>While debugging</strong>: To quickly reproduce issues without waiting for full data processing.</p><h3>When Full Data Matters</h3><p>Of course, sample mode isn’t appropriate everywhere. Before merging to production, run your full test suite against complete datasets. Use sample mode for speed during development, but validate thoroughly before deployment.</p><p>Similarly, for data quality checks that need to catch rare edge cases, or for aggregations where sampling might skew results, stick with full builds.</p><img src="https://cdn-images-1.medium.com/max/800/1*AZE0cFcN-rC1GLrwo7XhlA.png" alt="" /><h3>Important Limitations</h3><p>Keep in mind that sample mode:</p><ul><li>Is <strong>not currently available for Python models</strong> — the flag will be ignored if used</li><li>Uses <strong>time-based sampling only</strong> — you need timestamp columns configured via <code>event_time</code></li><li>May not populate all joins if your time ranges don’t align perfectly across tables</li><li>Seeds are created normally but sampled when referenced by downstream models</li></ul><h3>References</h3><a href="https://docs.getdbt.com/docs/build/sample-flag" title="https://docs.getdbt.com/docs/build/sample-flag"><strong>About the sample flag | dbt Developer Hub</strong><br><em>Use the sample flag to lower development time and reduce warehouse spend.</em>docs.getdbt.com</a><a href="https://docs.getdbt.com/docs/build/sample-flag" style="background-image: url(https://cdn-images-1.medium.com/fit/c/160/160/0*CCu40FbZSWLNuGOQ);"></a><a href="https://github.com/dbt-labs/dbt-core/discussions/11200" title="https://github.com/dbt-labs/dbt-core/discussions/11200"><strong>Sample Mode (for faster Development and CI 🚀) · dbt-labs dbt-core · Discussion #11200</strong><br><em>Have you ever wanted to run a smaller slice of your project during development?
