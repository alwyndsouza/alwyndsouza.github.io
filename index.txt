17:T232a,<p>I treat agile story skills like software. That means I test them, score them, and grade them — using <a href="https://promptfoo.dev">promptfoo</a> — before users hit a regression.</p>
<p>Here is why that matters. A skill can look solid in a demo, then quietly drift after a model upgrade, prompt edit, or when a new edge case sneaks in. One day it produces crisp acceptance criteria. The next day it forgets a required section, writes vague success criteria, or falls back to “as a user” even though the repository explicitly forbids that pattern. The goal is not proving prompts are perfect. The goal is catching regressions before users rely on broken output.</p>
<p>This article uses one skill as the example: agile-story-writer.</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*_PwC0iHlsGCklXSzlzREMw.png" alt=""></p>
<p>Image created using chatgpt</p>
<h3>The Skill: Agile Story Writer</h3>
<p>agile-story-writer turns a product or engineering request into a delivery-ready agile story. The skill should reliably produce:</p>
<ul>
<li>A deterministic box format</li>
<li>A specific persona – never the generic “as a user”</li>
<li>A clear story title starting with an action verb</li>
<li>Acceptance criteria in GIVEN / WHEN / THEN format</li>
<li>Scope In and Scope Out sections</li>
<li>Definition of Ready</li>
<li>Definition of Done</li>
<li>Measurable non-functional requirements</li>
</ul>
<p>That sounds straightforward, but it is exactly where prompt drift hides. A model can produce something that <em>looks</em> like a story while still being vague, hard to test, or structurally broken.</p>
<h3>What Goes Into an Eval Run</h3>
<p>The main eval lives at evals/agile-story-writer.yaml.</p>
<p>The chat prompt wrapper lives at evals/prompts/agile-story-writer.yaml.</p>
<p>The source skill instructions live at .github/skills/agile-story-writer/SKILL.md.</p>
<p>Promptfoo loads the skill instructions, sends test inputs, captures model outputs, and then checks those outputs with assertions. The flow looks like this:</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*5ZTkJL7A_X94gLkih2lB4Q.png" alt=""></p>
<p>The candidate model is driven by an EVAL_MODEL environment variable, so the same eval runs against Anthropic, OpenAI, Google, OpenRouter, or any other promptfoo-supported provider.</p>
<h3>Test, Score, Grade — Why I Separate Them</h3>
<p>These three terms are easy to blur. I keep them distinct:</p>
<p><strong>Test</strong> — Run a fixed input through the skill.</p>
<p><strong>Score</strong> — Use deterministic assertions to mark checks as pass or fail.</p>
<p><strong>Grade</strong> — Use an LLM rubric to judge qualitative output quality.</p>
<p>Here is a concrete example:</p>
<ul>
<li><em>Input:</em> Write a story for adding alerts on failed ingestion jobs.</li>
<li><em>Test:</em> Promptfoo sends that input to agile-story-writer.</li>
<li><em>Score:</em> Promptfoo checks that required sections exist and banned phrases do not appear.</li>
<li><em>Grade:</em> An LLM rubric checks whether the title, acceptance criteria, points estimate, and NFRs are actually good.</li>
</ul>
<p>That combination gives more signal than manual review alone.</p>
<h3>Deterministic Assertions: The Cheap, Reliable Layer</h3>
<p>Promptfoo scoring starts with deterministic assertions — exact structural checks using contains and not-contains rules.</p>
<p>For agile-story-writer, these include:</p>
<pre><code># Required structure must be present
- type: contains
  value: &quot;╔══&quot;
- type: contains
  value: &quot;AGILE STORY&quot;
- type: contains
  value: &quot;GIVEN&quot;
- type: contains
  value: &quot;WHEN&quot;
- type: contains
  value: &quot;THEN&quot;
- type: contains
  value: &quot;Scope - IN&quot;
- type: contains
  value: &quot;Scope - OUT&quot;
- type: contains
  value: &quot;DEFINITION OF READY&quot;
- type: contains
  value: &quot;DEFINITION OF DONE&quot;

# Forbidden anti-patterns must not appear
- type: not-contains
  value: &quot;as a user&quot;
</code></pre><p>These assertions are cheap and fast. If the model drops the required output shape, the test fails immediately without needing a grader model call. This gives structural scoring — I can tell whether the output still follows the expected story template before spending tokens on quality evaluation.</p>
<h3>LLM Rubrics: Catching Quality Drift, Not Just Structure</h3>
<p>Structure is necessary, but structure is not enough. A weak story can still contain GIVEN, WHEN, and THEN while being vague or untestable. That is why I layer in llm-rubric assertions.</p>
<p>For agile-story-writer, rubric checks ask a grader model questions like:</p>
<ul>
<li>Does the title start with an action verb such as Add, Build, Create, Fix, Migrate, or Expose?</li>
<li>Does the story have at least three acceptance criteria?</li>
<li>Is each acceptance criterion written in GIVEN / WHEN / THEN format?</li>
<li>Does each THEN clause describe something specific and testable?</li>
<li>Does the points field use a Fibonacci estimate with a rationale?</li>
<li>Does the NFR table include specific, measurable performance, security, and observability entries?</li>
</ul>
<p>The grader is not checking whether labels exist. It is checking whether output quality meets the bar. That is the grading layer — and it is where prompt drift that survives structural checks finally gets caught.</p>
<h3>How CI Uses Promptfoo — Without Fake Passes</h3>
<p>The CI workflow lives at .github/workflows/automated-evaluation.yml. It runs on pull requests that touch skill, agent, eval, package, or script files.</p>
<p>Model selection works through repository secrets in priority order:</p>
<ol>
<li>EVAL_MODEL when explicitly set</li>
<li>Anthropic default when ANTHROPIC_API_KEY exists</li>
<li>OpenAI default when OPENAI_API_KEY exists</li>
<li>Google default when GOOGLE_API_KEY exists</li>
<li>OpenRouter default when OPENROUTER_API_KEY exists</li>
</ol>
<p>If no provider key exists, CI skips live evals with a visible warning. It does not silently pass with mock output. That distinction matters — a skipped eval should be visible. A fake pass is worse than no eval at all.</p>
<h3>Reading Failures: Where to Look First</h3>
<p>Not every failure means the skill prompt is wrong. Reading the actual output is always the right first step.</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*TjngNRQBoNnBlrbKQW5fqg.png" alt=""></p>
<h3>How This Pattern Extends to Other Skills</h3>
<p>agile-story-writer is one example. The same structure applies across the full suite:</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*XyUGLk2FUowgZ5UqTAFXtg.png" alt=""></p>
<p>Each suite has different assertions and rubrics, but the same core pattern: fixed input → model output → structural score → quality grade → pass/fail.</p>
<h3>What I Would Add Next</h3>
<p>The current setup catches structural and quality regressions reliably. What it does not yet do is track <em>trends</em> — whether quality scores are slowly degrading across model versions rather than failing hard on a single run. The next evolution I am considering is storing rubric scores as numeric values over time so I can spot slow drift before it becomes a failure.</p>
<p>The other gap is cross-provider parity testing: running the same suite against two models simultaneously and flagging where rubric scores diverge significantly. That would make model upgrade decisions much more data-driven.</p>
<p>The pattern is solid. The tooling is mature enough to build on.</p>

<p>They happen because teams begin implementation before alignment exists.</p>
<p>A vague requirement enters backlog refinement, gets converted into stories too quickly, and turns into sprint commitments that optimise delivery activity instead of business outcomes. The result is predictable: teams complete tickets but still miss the actual objective.</p>
<p>This is where the <strong>sprint-goal-writer</strong> and <strong>problem-framing</strong> Agent Skills become valuable.</p>
<p>Rather than treating sprint planning as a story aggregation exercise, these skills introduce structured problem definition and outcome-driven sprint goals directly into the developer workflow.</p>
<p>The goal is simple:</p>
<blockquote>
<p><em>Define the right problem before delivery starts, then ensure the sprint has a measurable outcome once work is committed.</em></p>
</blockquote>
<h3>Why Most Sprint Goals Fail</h3>
<p>Many sprint goals are simply renamed task lists.</p>
<p>Examples like:</p>
<p><em>“Complete payment integration and finish notification service.”</em></p>
<p>do not provide:</p>
<ul>
<li>direction,</li>
<li>prioritisation guidance,</li>
<li>or meaningful trade-off leverage during the sprint.</li>
</ul>
<p>When blockers appear or scope changes, these goals collapse because they describe <em>activities</em>, not <em>outcomes</em>.</p>
<p>A strong sprint goal should answer:</p>
<p><em>“What meaningful change will exist for the customer or business at the end of this sprint?”</em></p>
<p>That distinction changes how teams plan, prioritise, and make delivery decisions.</p>
<h3>The sprint-goal-writer Agent Skill</h3>
<p>The <strong>sprint-goal-writer</strong> skill converts committed sprint stories into a concise, outcome-oriented sprint objective aligned with Scrum principles.</p>
<p>Instead of summarising tickets, it synthesises:</p>
<ul>
<li>business intent,</li>
<li>user impact,</li>
<li>and delivery scope</li>
</ul>
<p>into a single operational goal.</p>
<p>Example transformation:</p>
<h4>Weak Sprint Goal</h4>
<p><em>Complete authentication refactor and implement notifications.</em></p>
<h4>Strong Sprint Goal</h4>
<p><em>Enable customers to receive real-time transaction updates after completing purchases, reducing support dependency through improved visibility.</em></p>
<p>The second version provides the following:</p>
<ul>
<li>a user outcome,</li>
<li>a measurable direction,</li>
<li>and a decision-making framework for the sprint team.</li>
</ul>
<h3>The Five-Point Sprint Goal Validation Model</h3>
<p>Every generated sprint goal is evaluated against five validation checks.</p>
<h4>1. Single Sentence</h4>
<p>The goal should be concise enough to communicate clearly during standups and sprint reviews.</p>
<h4>2. Outcome-Oriented</h4>
<p>It must describe a result, not implementation tasks.</p>
<h4>3. Beneficiary-Focused</h4>
<p>The goal should clearly identify who benefits from the outcome.</p>
<h4>4. Measurable or Directional</h4>
<p>Teams should be able to determine whether the goal was achieved.</p>
<h4>5. Trade-Off Enabling</h4>
<p>The goal should help teams decide what matters most when priorities shift mid-sprint.</p>
<p>This transforms sprint goals from planning artefacts into operational alignment tools.</p>
<p><img src="https://cdn-images-1.medium.com/max/938/1*cT-cTfZYjKtP9kkugn9zzg.png" alt=""></p>
<h3>Problem Framing Before Sprint Planning</h3>
<p>The sprint goal skill works best when paired with the <strong>problem-framing</strong> Agent Skill.</p>
<p>This skill implements the MITRE Problem Framing Canvas — a structured framework used to refine vague requests into actionable problem definitions before stories are written.</p>
<p><img src="https://cdn-images-1.medium.com/max/840/1*BbSO6fer3YFOydp8Co0mDQ.png" alt=""></p>
<p>The framework moves through three stages:</p>
<h4>Phase 1 — Look Inward</h4>
<ul>
<li>Current state</li>
<li>Desired state</li>
<li>Gap analysis</li>
</ul>
<h4>Phase 2 — Look Outward</h4>
<ul>
<li>Stakeholders</li>
<li>Constraints</li>
<li>Risks and assumptions</li>
</ul>
<h4>Phase 3 — Reframe</h4>
<ul>
<li>Refined problem statement</li>
<li>“How Might We” (HMW) question</li>
</ul>
<p>The HMW question becomes the bridge between business intent and implementation planning.</p>
<p>Instead of asking:</p>
<p><em>“How do we build feature X?”</em></p>
<p>teams begin asking:</p>
<p><em>“How might we improve customer onboarding while reducing support dependency and maintaining compliance constraints?”</em></p>
<p>That shift dramatically improves backlog quality before engineering effort begins.</p>
<h3>The End-to-End Workflow</h3>
<p>The complete workflow becomes:</p>
<h4>1. Problem Framing</h4>
<p>Convert vague business requests into refined problem statements and HMW questions.</p>
<h4>2. Story Generation</h4>
<p>Generate structured agile stories aligned with the framed problem.</p>
<h4>3. Story Splitting</h4>
<p>Automatically decompose oversized stories into vertically sliced deliverables.</p>
<h4>4. Sprint Goal Definition</h4>
<p>Generate a measurable sprint outcome aligned with customer or business impact.</p>
<p>This creates a delivery pipeline focused on:</p>
<ul>
<li>alignment,</li>
<li>clarity,</li>
<li>and measurable outcomes.</li>
</ul>
<p>Not just ticket throughput.</p>
<h3>Practical Use Cases</h3>
<h4>During Sprint Planning</h4>
<p>Paste committed stories into /sprint-goal-writer to generate an outcome-focused sprint goal.</p>
<h4>During Retrospectives</h4>
<p>Run historical sprint goals through the validation model to identify weak planning patterns.</p>
<h4>During Discovery</h4>
<p>Use /problem-framing before backlog refinement to reduce ambiguity and improve stakeholder alignment.</p>
<h4>During Scope Trade-Offs</h4>
<p>Use the sprint goal as the prioritisation anchor when blockers or scope changes occur.</p>
<h3>Why This Matters</h3>
<p>High-performing agile teams are not defined by velocity alone.</p>
<p>They are defined by:</p>
<ul>
<li>clarity of intent,</li>
<li>shared understanding,</li>
<li>and disciplined decision-making.</li>
</ul>
<p>Agent Skills like problem-framing and sprint-goal-writer do more than automate documentation.</p>
<p>They encode delivery discipline directly into the engineering workflow.</p>
<p>The result is:</p>
<ul>
<li>better sprint alignment,</li>
<li>fewer misinterpreted requirements,</li>
<li>stronger backlog quality,</li>
<li>and more outcome-driven delivery cycles.</li>
</ul>
