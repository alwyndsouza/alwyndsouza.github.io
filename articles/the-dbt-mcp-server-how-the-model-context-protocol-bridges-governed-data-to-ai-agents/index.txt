<p>LLMs are smart but blind. Your semantic layer is organised but silent. MCP is the bridge that lets AI see your data — and answer questions without hallucinating.</p>
</blockquote>
<h3>The Promise and the Problem of “Chat With Your Data”</h3>
<p>Every data platform now offers some version of the same pitch: “Ask questions about your data in natural language. No SQL required.”</p>
<p>The promise is compelling. A business user types “How did we perform last quarter?” and gets an accurate, well-formatted answer — no tickets, no waiting, no SQL expertise needed.</p>
<p>The reality, in most implementations, is far less reliable.</p>
<p>When a large language model generates SQL against your warehouse, it’s guessing. It guesses at table names based on column headers it can see. It guesses at join paths based on naming conventions. It guesses at how to aggregate, what filters to apply, what time grain to use, and how to handle nulls. Sometimes the guesses are right. Often they’re subtly wrong. And the failure mode is insidious — <strong>the LLM returns a number that looks plausible but is silently incorrect</strong>.</p>
<p>This isn’t a model intelligence problem. GPT-4, Claude, Gemini — they’re all sophisticated enough to write syntactically correct SQL. The problem is <strong>context</strong>. The LLM doesn’t know your organisation’s metric definitions, your business logic conventions, your join hierarchies, or your data quality rules. It’s working from column names and whatever patterns it absorbed during training.</p>
<p>That’s not enough for analytics you can trust.</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*uJDWEdQ88GIyH_WcfYxtSQ.png" alt=""></p>
<h3>What’s Missing: Structured Context</h3>
<p>The gap between “AI that writes SQL” and “AI that gives trustworthy answers” is <strong>structured context – the governance layer</strong> that defines how your data is modelled, tested, and interpreted.</p>
<p>In the below articles,</p>
<ul>
<li><a href="https://aradsouza.medium.com/why-data-teams-need-a-semantic-layer-83947a5a0057">Why Data Teams Need a Semantic Layer</a></li>
<li><a href="https://aradsouza.medium.com/metrics-as-code-building-a-semantic-layer-with-dbt-and-metricflow-93d7e29e6ab3">Metrics as Code: Building a Semantic Layer With dbt and MetricFlow</a></li>
</ul>
<p>I covered how a <strong>semantic layer</strong> provides this governance for human consumers: metrics defined as code, version-controlled in Git, served consistently to every dashboard and report. If you’ve built a semantic layer with dbt and MetricFlow, you already have the hardest piece.</p>
<p>What’s been missing is the <strong>bridge – a</strong> way to make that governed context machine-readable so that AI agents can access the same definitions, the same metrics, and the same lineage that your human analysts use.</p>
<p>That’s what the <strong>dbt MCP Server</strong> provides.</p>
<h3>What Is MCP?</h3>
<p>The <strong>Model Context Protocol (MCP)</strong> is an open standard, originally released by Anthropic in late 2024, that defines how AI systems access external tools, data, and context at query time.</p>
<h4>A Simple Analogy</h4>
<p>Think of MCP as a <strong>USB-C port for AI</strong>. Before USB-C, every device had its own proprietary connector. You needed a different cable for every phone, camera, and laptop. USB-C standardised the interface — one port, universal compatibility.</p>
<p>MCP does the same for AI-to-data connections. Instead of building custom integrations for every AI tool — one connector for Claude, another for ChatGPT, another for Cursor, another for your internal copilot — you expose your data through a single MCP server. Any MCP-compatible client can plug in.</p>
<h4>How MCP Differs From Direct Database Access</h4>
<p>In a traditional “text-to-SQL” setup, the AI gets a database connection and writes SQL directly. This is powerful but ungoverned — there’s nothing between the LLM’s best guess and your production warehouse.</p>
<p>MCP works differently. Instead of raw database access, the AI gets a <strong>menu of tools</strong> — discrete, well-defined functions it can call, each with clear inputs and outputs. The AI selects the appropriate tool, passes in parameters, and gets back structured results.</p>
<p>This is fundamentally safer. The AI doesn’t have the freedom to write arbitrary SQL. It can only perform the operations you’ve exposed through tools. And because you control the tool definitions, you control the governance boundary.</p>
<h3>What the dbt MCP Server Exposes</h3>
<p>The dbt MCP Server takes everything in your dbt project — models, metrics, documentation, lineage, tests, semantic layer definitions — and wraps it in MCP tools that AI agents can call.</p>
<p>These tools fall into three categories, and understanding each is important for designing effective AI-over-data experiences.</p>
<h3>Discovery Tools: Letting AI Understand Your Data</h3>
<p>Before an AI agent can answer questions, it needs to understand what data exists and how it’s organised. Discovery tools provide this orientation:</p>
<ul>
<li><strong>Model exploration</strong> — list all models in the project, get details for specific models, explore mart-level models that are designed for consumption</li>
<li><strong>Lineage navigation</strong> — trace upstream dependencies (“where does this data come from?”) and downstream impacts (“what breaks if this table changes?”)</li>
<li><strong>Documentation access</strong> — read model descriptions, column descriptions, ownership metadata, freshness information</li>
<li><strong>Semantic search</strong> — find relevant models even when the user’s question doesn’t match an exact table or column name</li>
</ul>
<p>Think of this as giving a new analyst a thorough onboarding. Before answering a single question, the AI builds a contextual understanding of your data landscape — what exists, how it connects, who owns it, and what it means.</p>
<h3>Semantic Layer Tools: Querying Governed Metrics</h3>
<p>This is the critical differentiator. These tools connect directly to the governed metrics defined in your semantic layer:</p>
<ul>
<li><strong>List metrics</strong> — discover what business metrics are available</li>
<li><strong>Get dimensions</strong> — understand how a given metric can be sliced (by time, region, product category, etc.)</li>
<li><strong>Get entities</strong> — understand the join keys and relationships available for a metric</li>
<li><strong>Query metrics</strong> — execute a metric query and return governed results</li>
<li><strong>Get compiled SQL</strong> — inspect the exact SQL that MetricFlow generates, without executing it</li>
</ul>
<p>When the AI calls query_metrics, it&#39;s not writing SQL. MetricFlow generates the SQL from your YAML definitions. The result is <strong>correct by construction</strong> — it&#39;s derived from the same definitions that power your dashboards.</p>
<p>This is the difference between an AI that hallucinates numbers and one that returns answers grounded in your source of truth.</p>
<h3>Execution Tools: Operating on Your dbt Project</h3>
<p>For development and operational workflows, the MCP server also exposes dbt CLI tools:</p>
<ul>
<li><strong>Build, run, test</strong> — execute models, run data tests, validate quality</li>
<li><strong>Compile</strong> — generate SQL from models without executing, useful for review and validation</li>
<li><strong>Parse</strong> — check project files for syntax correctness</li>
<li><strong>Show</strong> — execute ad-hoc SQL and return results</li>
<li><strong>Generate</strong> — scaffold new model YAML, source definitions, and staging models</li>
</ul>
<p>These tools enable a new class of use case: <strong>agentic development</strong>. AI agents that don’t just query your data but develop your dbt project — refactoring models, running tests, and validating changes against your existing governance framework.</p>
<h3>The Key Architectural Principle</h3>
<p>There’s one principle that makes the entire architecture work, and it’s worth stating explicitly:</p>
<blockquote>
<p>The LLM never writes raw SQL. It calls governed tools through MCP. The SQL is generated by MetricFlow from your governed definitions.</p>
</blockquote>
<p>In a typical “text-to-SQL” approach:</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*zF_KgOsSz81Mo1cU9zpYSw.png" alt=""></p>
<p>With the dbt MCP Server and semantic layer:</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*K1aQGafRJLyM2LfwSNsAlA.png" alt=""></p>
<p>The LLM’s job shifts from <strong>SQL generation</strong> (error-prone, ungoverned) to <strong>intent interpretation</strong> (what metric does the user want? what dimensions? what filters?) and <strong>tool selection</strong> (which MCP tool should I call?). These are tasks LLMs are genuinely good at.</p>
<p>The SQL generation — the part that requires deep knowledge of your schema, join paths, business logic, and platform-specific syntax — is handled by MetricFlow, which has that knowledge encoded in your YAML definitions.</p>
<blockquote>
<p><strong>This separation of concerns is why the architecture produces trustworthy results.</strong></p>
</blockquote>
<h3>Local vs. Remote: Two Deployment Models</h3>
<p>The dbt MCP Server supports two deployment modes, each suited to different use cases.</p>
<h3>Local MCP Server</h3>
<p>The local server runs on your machine alongside your dbt project. It provides full access to dbt CLI commands and works with dbt Core, the dbt CLI, and the dbt Fusion engine.</p>
<p><strong>Best for:</strong></p>
<ul>
<li>Individual development workflows with tools like Cursor, Claude, or VS Code</li>
<li>Full CLI access including build, run, test, and compile</li>
<li>Working with local dbt projects without requiring a cloud account</li>
<li>Proof-of-concept exploration and validation</li>
</ul>
<p><strong>Trade-off:</strong> It’s tied to a single developer’s machine. Not suited for multi-user or production deployments.</p>
<h3>Remote MCP Server</h3>
<p>The remote server connects to the dbt platform via HTTP. No local installation required.</p>
<p><strong>Best for:</strong></p>
<ul>
<li>Production AI applications serving multiple users</li>
<li>Web applications and organisational-scale agent deployments</li>
<li>Consumption-focused use cases (querying metrics, exploring metadata, viewing lineage)</li>
<li>Environments where local software installation is restricted</li>
</ul>
<p><strong>Trade-off:</strong> Primarily consumption-oriented. The full development CLI tools aren’t available through the remote server.</p>
<p>For most teams, the journey starts local (POC and development) and moves remote (production and organisational scale).</p>
