<p>A “Software Engineering” mindset for data, without the infrastructure tax.</p>
</blockquote>
<p>The landscape of Databricks automation is shifting. With the release of <strong>Databricks CLI v0.279.0</strong>, a new era of “Direct Deployment” has arrived, signalling the eventual retirement of the Terraform-based backend for asset bundles.</p>
<p>Databricks is deprecating the Terraform engine and will require the Direct Deployment Engine as the <strong>sole supported path in 2026</strong>. If you’ve struggled with registry connection errors in locked-down environments or found Terraform state management too heavy for simple ETL pipelines, this change is for you.</p>
<p><img src="https://cdn-images-1.medium.com/max/1024/1*1vVtx7puXhu5vjjZR8yAOA.png" alt=""></p>
<p>self contained bundle</p>
<h3>What are Declarative Automation Bundles (DABs)?</h3>
<p>Declarative Automation Bundles – formerly Databricks Asset Bundles – are the recommended approach for packaging workspace resources like jobs, DLT pipelines, and notebooks. Think of them as <strong>Infrastructure-as-Code (IaC) tailored specifically for the analytics layer.</strong></p>
<p>A typical databricks.yml defines your resources simply:</p>
<pre><code>bundle:
  name: my_etl_pipeline
resources:
  jobs:
    daily_ingest:
      name: &quot;Daily Ingestion Job&quot;
      tasks:
        - task_key: ingest
          notebook_task:
            notebook_path: ./notebooks/ingest.py
targets:
  dev:
    workspace:
      host: https://my-dev-workspace.databricks.com
</code></pre><p>While the model is elegant, the underlying mechanism — Terraform — historically introduced significant friction for enterprise engineering teams.</p>
<h3>The Terraform Dependency: Where It Broke Down</h3>
<p>Until now, DABs acted as a wrapper for Terraform. Every bundle deploy trigger initiated a heavy sequence: downloading the Terraform binary, fetching the provider from registry.terraform.io, and generating internal state files.</p>
<p>For teams in <strong>regulated sectors like telecom, finance, or healthcare,</strong> this architecture created three primary headaches:</p>
<ul>
<li><strong>The Air-Gap Problem:</strong> CI/CD agents in restricted zones often lack outbound internet access, leading to the dreaded Could not retrieve provider error.</li>
<li><strong>The Skills Gap:</strong> Data engineers shouldn’t need to be Terraform experts to deploy a notebook. Managing provider mirrors and complex state files adds unnecessary overhead.</li>
<li><strong>The Version Lag:</strong> Supporting new Databricks features meant waiting for the Terraform provider to update before those resources could be automated.</li>
</ul>
<h3>The Direct Deployment Engine: Architecture and Advantages</h3>
<p>The <strong>Direct Deployment Engine</strong> eliminates the middleman. Instead of generating Terraform config and shelling out to terraform apply, the CLI now performs direct CRUD operations against Databricks REST APIs using the native Go SDK.</p>
<p>The result is a <strong>self-contained binary</strong>. No Terraform download. No provider registry. No proxy issues.</p>
<h3>Adopting Direct Deployment</h3>
<h3>Option 1: New Bundles (Never Deployed Before)</h3>
<p>For fresh projects, opt-in by setting an environment variable or updating your configuration:</p>
<p><strong>Via Environment Variable:</strong></p>
<pre><code>export DATABRICKS_BUNDLE_ENGINE=direct 
databricks bundle deploy -t dev
</code></pre><p><strong>Via</strong> <strong>databricks.yml:</strong></p>
<pre><code>bundle:
  name: my_pipeline
  engine: direct  # Sets the default for all targets
</code></pre><h3>Option 2: Migrating Existing Bundles</h3>
<p>If you already have bundles deployed via Terraform, you must migrate your state file. The Direct Engine uses a new JSON schema (resources.json) rather than terraform.tfstate.</p>
<p><strong>Sync:</strong> Ensure your current environment is fully synced.</p>
<p>databricks bundle deploy -t my_target.</p>
<p><strong>Migrate:</strong> Convert the state file:</p>
<p>databricks bundle deployment migrate -t my_target.</p>
<p><strong>Verify:</strong> Confirm zero planned changes.</p>
<p>databricks bundle plan -t my_target.</p>
<ul>
<li><strong>Finalise:</strong> Deploy to lock in the new state.</li>
</ul>
<blockquote>
<p><em><strong>Note:</strong></em> <em>The migration command still needs to read the old Terraform state, so run this step in an environment with internet access before moving the bundle to a locked-down zone</em></p>
</blockquote>
<h3>Where Terraform Still Belongs</h3>
<p>This is not a deprecation of Terraform itself. Terraform remains the best tool for <strong>platform infrastructure</strong> — the foundation that sits beneath your workloads:</p>
<ul>
<li><strong>Compute and Networking:</strong> VPCs, subnets, and security groups.</li>
<li><strong>Workspace Provisioning:</strong> Creating the workspace and Unity Catalog metastores.</li>
<li><strong>Identity:</strong> Service principals, IAM roles, and group memberships.</li>
</ul>
<p><strong>The emerging best practice is clear:</strong> use Terraform for infrastructure provisioning and use DABs (with the direct engine) for analytics asset deployment. These are complementary layers, not competing tools.</p>
<blockquote>
<p>The transition from Terraform to direct deployment is a signal of where Databricks is headed: a streamlined developer experience that removes friction between your code and your workspace. For data engineering teams, the action items are clear: <strong>Evaluate the direct engine on non-production targets now</strong> to ensure your pipelines are future-proofed for 2026.</p>
</blockquote>
