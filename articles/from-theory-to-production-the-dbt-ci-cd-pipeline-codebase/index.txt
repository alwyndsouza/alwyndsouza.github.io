<h3><strong>High Level Architecture</strong></h3>
<p>This below diagram provides comprehensive overview of the dbt CI/CD system architecture, detailing how automated pipelines, code quality systems, and infrastructure components work together to enable reliable data transformation development and deployment. The architecture implements enterprise-grade practices including isolated testing environments, state-aware deployments, and multi-layered quality assurance.</p>
<h3>Pipeline Architecture Overview</h3>
<p>The CI/CD system implements a two-stage pipeline architecture with clear separation between validation and deployment concerns.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*M30rTSggIXh7FyHft3s4mg.png" alt=""></p>
<h3><strong>CI Pipeline</strong></h3>
<p>The CI pipeline serves as the primary quality gate for all code changes, implementing a multi-stage validation process that prevents broken code from reaching production. The pipeline runs automatically on pushes to development branches and pull requests, providing immediate feedback to developers.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*jPwPfnHR8hZ13jCi6DBm9g.png" alt=""></p>
<h4>Trigger Conditions and Concurrency Management</h4>
<p>The pipeline uses sophisticated trigger conditions and concurrency controls to optimize resource usage and provide fast feedback.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*kRvbpPP8P4sT0ZxJpfh1yA.png" alt=""><img src="https://cdn-images-1.medium.com/max/800/1*lz9GfyJDMCvBYtlB1y_eGg.png" alt=""></p>
<h4>Dynamic Schema Management</h4>
<p>One of the most sophisticated features of the CI pipeline is its dynamic schema creation for test isolation.</p>
<p>Schema Generation Logic The dynamic schema naming is implemented.</p>
<ul>
<li>Pull Requests: <code>pr_{PR_NUMBER}_{COMMIT_SHA}</code></li>
<li>Branch Pushes: <code>{BRANCH_NAME}_{COMMIT_SHA}</code> (with special character sanitization)</li>
</ul>
<p>Cleanup Process The pipeline ensures proper resource cleanup by always running the schema cleanup step even if the build fails:</p>
<pre><code>dbt run-operation drop_schema --args &#x27;{ &quot;schema_name&quot;: &quot;${{ env.DBT_SCHEMA }}&quot; }&#x27;
</code></pre><p><img src="https://cdn-images-1.medium.com/max/800/1*1XstYNqTbjsqefNphWSV0w.png" alt=""></p>
<h4>dbt Build and Test Execution</h4>
<p>The core dbt validation job runs the complete build process in an isolated environment.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*ygOihQus9G8Szohut6eHsA.png" alt=""></p>
<h3><strong>CD Pipeline</strong></h3>
<p>The Continuous Deployment Pipeline is responsible for deploying validated dbt changes to the production environment. This system automatically triggers when code is merged to the main branch, performing state-aware deployments that only build modified models and their downstream dependencies.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*ioTEx_6t90FscvTMcRK_iw.png" alt=""></p>
<h4><strong>State-Aware Deployment Strategy</strong></h4>
<p>The pipeline implements intelligent deployment logic that minimizes execution time by only building modified models.</p>
<h4>Manifest Download and State Detection</h4>
<p>The deployment strategy uses the <code>Legit-Labs/action-download-artifact@v2</code> action to retrieve the previous production manifest:</p>
<ul>
<li>Artifact Name: <code>dbt-manifest-prod</code></li>
<li>Path: <code>prod-artifacts</code> directory</li>
<li>Workflow Source: <code>dbt-cd-pipeline.yml</code></li>
<li>Continue on Error: <code>true</code> (gracefully handles first deployment)</li>
</ul>
<p><img src="https://cdn-images-1.medium.com/max/800/1*8nVwmhkJ1vmxSxy_6r0Uxw.png" alt=""></p>
<h4>Build Execution Logic</h4>
<p>The build step implements conditional logic for optimal deployment:</p>
<pre><code># State-based build (when previous manifest exists)
</code></pre><p>This approach:</p>
<ul>
<li>Reduces deployment time by only building changed models and their dependencies</li>
<li>Maintains data consistency through the <code>state:modified+</code> selector</li>
<li>Enables safe rollback by deferring to previous state when possible</li>
<li>Handles first deployment gracefully with full build fallback</li>
</ul>
<h3>Artifact Management System</h3>
<p>The pipeline maintains deployment state through comprehensive artifact management.</p>
<h4><strong>Artifact Upload Strategy</strong></h4>
<p><img src="https://cdn-images-1.medium.com/max/800/1*78x3rmKcuBmxxBHMbkvMLg.png" alt=""></p>
<h4>Manifest Artifact</h4>
<ul>
<li>Name: <code>dbt-manifest-prod</code></li>
<li>Path: <code>target/manifest.json</code></li>
<li>Condition: Only on successful builds</li>
<li>Retention: 7 days</li>
<li>Purpose: Enables state-based deployments for subsequent runs</li>
</ul>
<h4>Results Artifact</h4>
<ul>
<li>Name: <code>dbt-results</code></li>
<li>Path: <code>dbt_results.md</code></li>
<li>Condition: Always uploaded (success or failure)</li>
<li>Retention: 7 days</li>
<li>Purpose: Provides deployment logs and debugging information</li>
</ul>
<h3>Development Workflow and Code Quality</h3>
<p>This document covers the development workflow and automated code quality enforcement systems that ensure consistent, high-quality code in the dbt project. It details the multi-layered quality gates from local development through CI/CD deployment, including pre-commit hooks, SQL linting, formatting standards, and automated validation processes.</p>
<h4><strong>Development Workflow Overview</strong></h4>
<p>The development workflow implements a multi-stage quality assurance process that validates code changes at multiple checkpoints before deployment.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*4QW73Yw_D9d0e6PNtxbuGA.png" alt=""></p>
<h4>Pre-commit Hook System</h4>
<p>The pre-commit system is configured via <code>.pre-commit-config.yaml</code> and provides comprehensive code quality validation through multiple specialized tools.</p>
<h4>Pre-commit Hook Execution Flow</h4>
<p><img src="https://cdn-images-1.medium.com/max/800/1*Pxsui-7s7r3_7NVlh17Bdw.png" alt=""></p>
<h4>Hook Categories and Configuration</h4>
<p><strong>Basic File Quality Checks</strong></p>
<p>These hooks ensure fundamental file consistency and prevent common issues:</p>
<ul>
<li><code>trailing-whitespace</code> Removes trailing whitespace from SQL, YAML, and Markdown files</li>
<li><code>end-of-file-fixer</code> Ensures files end with newlines</li>
<li><code>check-added-large-files</code> Prevents large files (&gt;1MB) from being committed</li>
<li><code>mixed-line-ending</code> Standardizes line endings to LF</li>
</ul>
<p><strong>Security Validation</strong></p>
<p>Security hooks prevent accidental exposure of sensitive information:</p>
<ul>
<li><code>gitleaks</code>Scans for secrets, API keys, and credentials</li>
<li><code>detect-private-key</code>Identifies private SSH keys</li>
<li><code>check-case-conflict</code> Prevents case-sensitivity issues</li>
</ul>
<p><strong>dbt-Specific Validation</strong></p>
<p>The <code>dbt-checkpoint</code> hooks ensure dbt best practices and project consistency:</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*w325oS2oIjFgnRI3Z_riCw.png" alt=""></p>
<h3>Git Hooks and Automation</h3>
<p>The Git hooks automation system provides a lightweight, fast quality gate that runs before commits are allowed to proceed. This system complements the more comprehensive pre-commit hooks by focusing on immediate file-level quality checks.</p>
<p><strong>Husky Git Hook Management</strong></p>
<p>Husky manages Git hooks through Node.js tooling, providing a reliable cross-platform solution for hook execution. The system is configured to run multiple validation steps automatically.</p>
<p><strong>Hook Configuration</strong></p>
<p>The pre-commit hook executes two primary validation steps:</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*g5nGa3R1EQ_30DqGtyB9ow.png" alt=""></p>
<p>The hook implementation runs both <code>lint-staged</code> for file-specific formatting and the broader pre-commit framework validation.</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*IlAS5N4cKgtSMB0gfWt1JQ.png" alt=""></p>
<p><strong>Lint-Staged Integration</strong></p>
<p>The <code>lint-staged</code> tool ensures only modified files are processed for formatting, improving performance by avoiding full-repository scans.</p>
<p><strong>File Pattern Configuration</strong></p>
<p>The system targets YAML configuration files across the repository:</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*64dEWG8ixLt8Qus6bXhNMw.png" alt=""></p>
<p>The configuration processes all <code>.yml</code> and <code>.yaml</code> files in the repository, automatically formatting them according to Prettier standards.</p>
<p><strong>Automation Scripts</strong></p>
<p>The package defines utility scripts for manual formatting operations:</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*r4ipKMr_TlyLQu9bkvQSBA.png" alt=""></p>
<h3>Workflow Integration</h3>
<p>The automation system integrates with the development workflow through multiple touchpoints:</p>
<p><img src="https://cdn-images-1.medium.com/max/800/1*jDo5UeQrpw2XUVAMjfA51A.png" alt=""></p>
<p><strong>Installation and Setup</strong></p>
<p>The system initializes automatically through the <code>prepare</code> script, which runs during <code>npm install</code>:</p>
<ol>
<li>Package installation triggers the <code>prepare</code> script</li>
<li><code>husky install</code> creates the <code>.husky</code> directory and hook files</li>
<li>Git hooks become active for the repository</li>
</ol>
<p><strong>Configuration Management</strong></p>
<p>The automation system relies on centralized configuration in <code>package.json</code> rather than distributed config files. This approach ensures consistent behavior across development environments.</p>
<h4>Hook Execution Order</h4>
<p>The pre-commit hook executes operations in a specific sequence:</p>
<ol>
<li><code>npx lint-staged</code> - Format staged YAML files</li>
<li><code>pre-commit run</code> - Execute broader validation suite</li>
</ol>
<p>This ordering ensures files are properly formatted before comprehensive validation begins.</p>
<h4>Performance Considerations</h4>
<p>The system is optimized for speed through several design decisions:</p>
<ul>
<li>Only staged files are processed by <code>lint-staged</code></li>
<li>YAML formatting is limited to configuration files</li>
<li>Parallel execution of independent validation steps</li>
</ul>
