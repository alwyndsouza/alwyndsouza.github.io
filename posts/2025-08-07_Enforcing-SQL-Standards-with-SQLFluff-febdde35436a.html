Welcome back to our dbt CI/CD series! In Article 2, we implemented pre-commit hooks for basic quality control. Now we'll add SQLFluff - a powerful SQL linter that will enforce consistent coding standards across your entire dbt project.

What is SQLFluff?

SQLFluff is a SQL linter and formatter that can understand various SQL dialects and templating languages, including dbt's Jinja templating. It enforces style rules, catches syntax errors, and can automatically fix many issues.

Step 1: Understanding SQLFluff Configuration

SQLFluff uses a .sqlfluff configuration file in your project root. This file defines the SQL dialect, templating engine, and all the linting rules.

Create .sqlfluff in your project root:

# .sqlfluff
# SQLFluff configuration for dbt project with Databricks

[sqlfluff]
# Databricks uses Spark SQL dialect
dialect = databricks
# Use dbt templater to understand Jinja
templater = dbt
# Maximum line length for SQL statements
max_line_length = 150
# Skip files larger than this to avoid performance issues
large_file_skip_byte_limit = 0
# File extensions to process
sql_file_exts = .sql
# Number of parallel processes (-1 = auto-detect CPU cores)
processes = -1
# Rules to exclude (we will customize these)
exclude_rules = CV11, AM02, AM06

[sqlfluff:templater:dbt]
# dbt-specific templater configuration
project_dir = .
profiles_dir = .
# Apply dbt built-in macros and functions
apply_dbt_builtins = True

[sqlfluff:indentation]
# Use 4 spaces for indentation
tab_space_size = 4
indent_unit = space
# Allow implicit indents (useful for long SELECT clauses)
allow_implicit_indents = True

[sqlfluff:rules:aliasing.table]
# Require explicit table aliases
aliasing = explicit

[sqlfluff:rules:aliasing.column]
# Require explicit column aliases when needed
aliasing = explicit

[sqlfluff:rules:aliasing.length]
# Minimum alias length (prevents single-letter aliases)
min_alias_length = 2

[sqlfluff:rules:capitalisation.keywords]
# Use lowercase for SQL keywords (SELECT, FROM, WHERE)
capitalisation_policy = lower

[sqlfluff:rules:capitalisation.identifiers]
# Use lowercase for identifiers (table names, column names)
extended_capitalisation_policy = lower

[sqlfluff:rules:capitalisation.functions]
# Use lowercase for functions (COUNT, SUM, AVG)
extended_capitalisation_policy = lower

[sqlfluff:rules:capitalisation.literals]
# Use lowercase for literals where applicable
capitalisation_policy = lower

[sqlfluff:rules:capitalisation.types]
# Use lowercase for data types (INT, VARCHAR, TIMESTAMP)
extended_capitalisation_policy = lower

[sqlfluff:rules:ambiguous.column_references]
# Require explicit table references in GROUP BY and ORDER BY
group_by_and_order_by_style = explicit

[sqlfluff:rules:layout.long_lines]
# Don't flag long lines in comments
ignore_comment_lines = true
ignore_comment_clauses = true

# Specific files that are hard to lint

Step 3: Understanding Key Configuration Sections

Dialect and Templater Configuration

[sqlfluff]
dialect = databricks
templater = dbt

Why Databricks?

  • Supports Spark SQL syntax
  • Handles Delta Lake specific functions
  • Compatible with most modern SQL features

Why dbt templater?

  • Understands Jinja syntax ({{ }}, {% %})
  • Resolves dbt functions like ref() and source()
  • Handles dbt configurations and variables

Indentation Rules

[sqlfluff:indentation]
tab_space_size = 4
indent_unit = space
allow_implicit_indents = True

This creates clean, readable SQL:

-- Good (follows our rules)
select
    customer_id,
    first_name,
    last_name,
    case 
        when status = 'active' 
        then 'Active Customer'
        else 'Inactive Customer'
    end as customer_status
from {{ ref('raw_customers') }}
where created_at >= '2023-01-01'

Capitalization Standards

[sqlfluff:rules:capitalisation.keywords]
capitalisation_policy = lower

Benefits of lowercase keywords:

  • More readable and modern
  • Consistent with Python/dbt conventions
  • Reduces visual noise in code

Aliasing Rules

[sqlfluff:rules:aliasing.table]
aliasing = explicit

[sqlfluff:rules:aliasing.length]
min_alias_length = 2

Enforces clear aliases:

-- Good ✅
select 
    cust.customer_id,
    ord.order_date
from {{ ref('customers') }} as cust
join {{ ref('orders') }} as ord
    on cust.customer_id = ord.customer_id

-- Bad ❌ (single letter alias)
select 
    c.customer_id,
    o.order_date
from {{ ref('customers') }} as c
join {{ ref('orders') }} as o
    on c.customer_id = o.customer_id

Step 4: Understanding Excluded Rules

exclude_rules = CV11, AM02, AM06

Let's understand why we exclude these:

CV11 - Implicit/Explicit Column References

What it checks: Ensures columns are explicitly referenced with table aliases Why we exclude: Can be overly strict for simple queries with single tables

AM02 - Ambiguous Column References

What it checks: Flags potentially ambiguous column names Why we exclude: Often flags false positives in dbt models

AM06 - Column References

What it checks: Various column reference patterns Why we exclude: Can conflict with dbt's templating patterns

Step 6: Create Sample Files for Testing

Let's create some sample SQL files to test our SQLFluff configuration:

Create a Poorly Formatted Model

Create models/staging/stg_orders_bad.sql:

-- models/staging/stg_orders_bad.sql
-- This file intentionally has formatting issues

{{config(materialized='view')}}

SELECT order_id, customer_id,order_date,   total_amount,STATUS
FROM {{source('raw','orders')}}
WHERE order_date>='2023-01-01' AND   status IN ('completed','shipped')
GROUP BY order_id,customer_id,order_date,total_amount,status
ORDER BY order_date DESC,total_amount

Test SQLFluff on the Bad File

# Lint the bad file
sqlfluff lint models/staging/stg_orders_bad.sql

You should see output like:

== [models/staging/stg_orders_bad.sql] FAIL
L:4 C:1: [CP01] Keywords must be consistently capitalised.
L:4 C:8: [LT05] Commas should not have whitespace directly before them.
L:4 C:21: [LT02] Expected line break but found space.
L:5 C:1: [CP01] Keywords must be consistently capitalised.
L:6 C:1: [CP01] Keywords must be consistently capitalised.

Fix the Issues Automatically

# Fix the file automatically
sqlfluff fix models/staging/stg_orders_bad.sql

The file should now look like:

-- models/staging/stg_orders_bad.sql
-- This file intentionally has formatting issues

{{ config(materialized='view') }}

select
    order_id,
    customer_id,
    order_date,
    total_amount,
    status
from {{ source('raw', 'orders') }}
where
    order_date >= '2023-01-01'
    and status in ('completed', 'shipped')
group by
    order_id,
    customer_id,
    order_date,
    total_amount,
    status
order by
    order_date desc,
    total_amount

Step 7: Advanced SQLFluff Configuration

Custom Rule Configuration

Add more specific rules to your .sqlfluff:

# Add to your .sqlfluff file

[sqlfluff:rules:structure.subquery]
# Require subqueries to be aliased
forbid_subquery_in_from_clause_without_alias = True

[sqlfluff:rules:references.special_chars]
# Allow underscores in identifiers
quoted_identifiers_policy = none
unquoted_identifiers_policy = all

[sqlfluff:rules:layout.select_targets]
# Put each SELECT item on its own line
wildcard_policy = single

dbt-Specific Configurations

[sqlfluff:templater:dbt]
project_dir = .
profiles_dir = .
apply_dbt_builtins = True

# Skip macro files (they often have complex Jinja)
[sqlfluff:rules:templater]
forbid_unused_placeholders = False

Step 9: Common SQLFluff Rules Explained

Layout Rules (LT)

  • LT01: Unnecessary trailing whitespace
  • LT02: Incorrect spacing around operators
  • LT05: Incorrect comma spacing
  • LT09: Select targets should be on separate lines

Capitalization Rules (CP)

  • CP01: Inconsistent keyword capitalization
  • CP02: Inconsistent function name capitalization
  • CP03: Inconsistent identifier capitalization

Structure Rules (ST)

  • ST01: Unnecessary else/elsif in CASE statements
  • ST02: Unnecessary comparison with boolean literals
  • ST03: Query defines a CTE but does not use it

Convention Rules (CV)

  • CV01: Use 'coalesce' instead of 'isnull' or 'nvl'
  • CV02: Use 'not' instead of '!=' or '<>'
  • CV03: Consistent trailing commas in select clauses

Step 10: Handling Complex dbt Patterns

Jinja in SQL

SQLFluff can handle most dbt Jinja patterns:

-- This works well with SQLFluff
select
    customer_id,
    {% if var('include_pii') %}
    email,
    phone_number,
    {% endif %}
    created_at
from {{ ref('raw_customers') }}
where
    {% if var('start_date') %}
    created_at >= '{{ var('start_date') }}'
    {% else %}
    created_at >= current_date - interval '30 days'
    {% endif %}

Macros and Complex Logic

For files with complex macros, you might need to exclude them:

-- models/complex_macro_model.sql
-- sqlfluff:disable

{{ my_complex_macro() }}

-- sqlfluff:enable

Or add to .sqlfluffignore:

models/complex_macro_model.sql

Step 12: Performance Optimization

Speed Up SQLFluff for Large Projects

# In your .sqlfluff file
[sqlfluff]
# Use multiple processes
processes = -1

# Skip large files
large_file_skip_byte_limit = 40000

# Only process SQL files
sql_file_exts = .sql

Selective Linting

# Only lint changed files
git diff --name-only --diff-filter=AM | grep '\.sql$' | xargs sqlfluff lint

# Only lint specific directories
sqlfluff lint models/marts/

Common Issues and Troubleshooting

Issue 1: dbt templating errors

Symptom: SQLFluff can't parse dbt Jinja templates Solution:

# Ensure dbt can compile the model first
dbt compile --select stg_customers

# Check your profiles.yml and environment variables
dbt debug

# Try linting with more verbose output
sqlfluff lint models/staging/stg_customers.sql --verbose

Issue 2: Too many false positives

Symptom: SQLFluff flags legitimate patterns as errors Solution:

# Add to .sqlfluff to exclude problematic rules
exclude_rules = CV11, AM02, AM06, LT01

# Or disable specific rules for specific files
# sqlfluff:disable=CV11

Issue 3: Performance issues

Symptom: SQLFluff is too slow on large projects Solution:

# Optimize performance in .sqlfluff
[sqlfluff]
processes = -1
large_file_skip_byte_limit = 20000

# Use .sqlfluffignore more aggressively
target/
dbt_packages/
seeds/

Issue 4: Complex macro parsing

Symptom: SQLFluff fails on complex dbt macros Solution:

-- Add to problematic files
-- sqlfluff:disable

-- Or exclude specific sections
-- sqlfluff:disable=all
{{ complex_macro_call() }}
-- sqlfluff:enable=all

Best Practices Summary

  1. Start Permissive: Begin with lenient rules, tighten gradually
  2. Team Consensus: Agree on style standards before enforcing
  3. Document Exceptions: Use comments to explain disabled rules
  4. Regular Maintenance: Update SQLFluff and review rules periodically
  5. IDE Integration: Set up real-time linting for better developer experience
