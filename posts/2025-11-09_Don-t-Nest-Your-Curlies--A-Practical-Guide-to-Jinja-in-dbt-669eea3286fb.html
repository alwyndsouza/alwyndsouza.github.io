Don’t Nest Your Curlies: A Practical Guide to Jinja in dbt

The most common syntax mistake in dbt projects — and how to avoid it

If you have worked with dbt for more than a week, you have probably encountered a frustrating debugging session where everything looks correct, but your model refuses to compile. The SQL is fine. The logic makes sense. The error message is cryptic.

Nine times out of ten, it’s nested curly braces.

The Problem

When writing Jinja in dbt, there’s a natural temptation to nest expressions inside each other. After all, we nest function calls constantly in programming. Why should template syntax be different?

Here’s a typical scenario: you’re using a macro and want to pass a dynamic value to it:

-- ❌ This seems reasonable, but it won't work
{{ dbt_utils.date_spine(
    datepart="day",
    start_date="{{ var('start_date') }}",
    end_date="{{ var('end_date') }}"
) }}

The problem? You’re not passing the variable’s value — you’re passing the literal string "{{ var('start_date') }}" to the macro. The macro receives the text "{{ var('start_date') }}", not an actual date value.

The correct way:

-- ✅ This works
{{ dbt_utils.date_spine(
    datepart="day",
    start_date=var('start_date'),
    end_date=var('end_date')
) }}

Understanding Jinja Context

The key concept is simple: once you open a Jinja expression with {{, everything inside is already being evaluated as Jinja code. You don't need additional delimiters.

Think of it like this: the curly braces are a gate into “Jinja mode.” Once you’re through the gate, you’re in. Opening another gate while you’re already inside doesn’t make sense.

Common Patterns That Trip People Up

Dynamic Table Names

-- ❌ Wrong - nested curlies in a string assignment
{% set table_name = "sales_{{ var('region') }}_daily" %}


-- ✅ Right - use the tilde (~) operator for concatenation
{% set table_name = "sales_" ~ var('region') ~ "_daily" %}

When you write {% set table_name = "..." %}, you're already inside a Jinja statement. Adding {{ }} inside that string doesn't evaluate the variable—it just creates a string containing those characters.

Macro Arguments

-- ❌ Wrong - nested curlies as macro parameters
{{ custom_macro(
    table_name="{{ ref('my_table') }}",
    column_name="{{ var('column') }}"
) }}


-- ✅ Right - pass the values directly
{{ custom_macro(
    table_name=ref('my_table'),
    column_name=var('column')
) }}

Building Dynamic SQL Strings

-- ❌ Wrong
{% set where_clause = "created_at >= '{{ var('start_date') }}'" %}

-- ✅ Right
{% set where_clause = "created_at >= '" ~ var('start_date') ~ "'" %}

Conditional Logic

-- ❌ Wrong
{% if "{{ var('environment') }}" == "prod" %}
    {{ ref('prod_table') }}
{% endif %}

-- ✅ Right
{% if var('environment') == "prod" %}
    {{ ref('prod_table') }}
{% endif %}

The One Exception: Hooks

There’s an important exception to this rule that confuses many developers: hooks actually require nested curlies.

{{ config(
    post_hook="GRANT SELECT ON {{ this }} TO ROLE reporting_role"
) }}

Why does this work? In hooks, you’re defining a string template that will be rendered later, after your model builds. You want the literal text "{{ this }}" to be stored as the hook configuration. When the hook executes, dbt will render that template in context, replacing {{ this }} with your actual table reference.

This is fundamentally different from other Jinja contexts where you want immediate evaluation.

Another valid hook example:

{{ config(
    pre_hook="INSERT INTO audit_log VALUES ('{{ this }}', '{{ run_started_at }}')"
) }}

Here, you’re storing a string with Jinja placeholders that will be evaluated when the hook runs.

Why This Matters

This syntax quirk isn’t just an academic concern — it has real impact:

  • Debugging time: These errors often produce unclear error messages, leading to lengthy troubleshooting sessions
  • Code reviews: Reviewers might miss these issues if they’re not specifically looking for them
  • Onboarding: New team members consistently stumble over this pattern
  • Production issues: These bugs can slip through development and cause runtime failures

Developing Good Habits

Here are some practices that help prevent this issue:

1. Default to simple expressions When in doubt, keep your Jinja expressions straightforward. Use the tilde operator (~) for concatenation rather than embedding expressions in strings.

2. Use set blocks for complex logic If you need to build something complicated, use a {% set %} block to construct it step by step:

{% set base_table = ref('orders') %}
{% set date_filter = var('start_date') %}

SELECT *
FROM {{ base_table }}
WHERE order_date >= '{{ date_filter }}'

3. Test incrementally When adding new Jinja logic, compile your model frequently (dbt compile) to catch syntax errors early.

4. Learn the mental model Understanding that curly braces define context — rather than thinking of them as “Jinja syntax that goes around Jinja code” — helps prevent these mistakes.

Quick Reference

Within Jinja expressions (inside {{ }} or {% %}), use:

  • var('variable_name') not {{ var('variable_name') }}
  • ref('model_name') not {{ ref('model_name') }}
  • "string" ~ variable not "string {{ variable }}"

Exception for hooks:

  • post_hook="SQL with {{ this }}" is correct because you're defining a template string to be rendered later

A Simple Mental Model

Here’s an easy way to remember:

  • Outside Jinja: Use {{ }} to enter Jinja mode
  • Inside Jinja: You’re already there — just use the functions directly
  • In hook strings: Use {{ }} because you're writing a template for future rendering
